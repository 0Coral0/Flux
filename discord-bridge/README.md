# Flux community service: Discord + Ollama

This worker serves the **Discord Chat**, **Discord DM**, and **Assistant** pages in Flux. It runs alongside the existing Wisp proxy on the VM, on a separate port. It does not replace the proxy. The former Firestore global-chat relay is superseded by this dedicated Discord interface; Global Chat remains Flux-only.

## What to set up

### Keep Flux online away from the PC

For a school-safe public setup, host the static website on Vercel and keep this long-running bridge on an always-on VM. The ready-to-use Docker, Caddy, and Oracle Always Free steps are in [DEPLOY-ORACLE-FREE.md](DEPLOY-ORACLE-FREE.md). Vercel cannot host the Discord gateway itself because its functions are not permanent processes. This guide prepares files only; it does not publish Flux or send any credentials anywhere.

If a no-card Render account is the only option, [RENDER-SETUP.md](../RENDER-SETUP.md) prepares the bridge to wake on the first request after idle. It is intentionally not an always-on production setup and does not run Ollama or the public browser proxy.

The main checkout includes a local, Git-ignored `discord-bridge/.env` copied from the template. Fill in that file on your server; it contains no working credentials yet. For a fresh clone, copy `.env.example` to `.env` first. The community service defaults to port **3032** so it can run beside the local Flux website on **3031** and browser proxy on **3040**.

From the repository root, install the worker dependencies with `npm --prefix discord-bridge ci`, then use `npm run start:community` after configuring `.env`. Set the public worker address in `js/discord-config.js`. Run `npm test` from the root to check the community service and website integration.

### Run on this Windows PC

Use **`Start Flux Community.cmd`** from the Flux folder, or `npm run start:community`. The launcher checks the private settings, starts the Discord service on loopback port 3032, opens an HTTPS Cloudflare quick tunnel, updates the local `js/discord-config.js`, and starts the local Flux website on port 3031 if needed. It uses the existing `proxy/.tools/cloudflared.exe`. It never commits or publishes changes automatically. Keep the launcher running while using the bridge; stopping it disconnects the website service and bot. A restart gives a new public address, so the hosted website needs the updated files/config published again. A stable named tunnel can be configured separately if you want a permanent address.

`npm --prefix discord-bridge run check:pc` checks for missing fields and files without printing secrets or starting a connection. For this PC, the server ID is already set to Flux (`1419014702037602506`). The missing items are the bot token and a local Firebase service-account JSON. Put the bot token in `.env` and point `GOOGLE_APPLICATION_CREDENTIALS` to the JSON's absolute path; keep both private. The launcher allows the exact local site origin `http://127.0.0.1:3031` alongside `FLUX_SITE_ORIGIN`.

1. **Discord application:** at https://discord.com/developers/applications create the Flux bot. Give it a permanent bot avatar you like, enable **Message Content Intent**, and invite it with the bot scope. Grant **View Channels**, **Read Message History**, **Send Messages**, and **Embed Links**. To reply to public threads or forum posts, also grant **Send Messages in Threads** in the intended channels. Set `DISCORD_GUILD_ID` to the server ID. Flux Bot has already been authorized in the Flux server with the first four permissions; thread posting still needs its extra permission if not inherited from the server's normal roles.
2. **Optional per-channel webhooks:** create a webhook in each writable channel where you want each Flux sender's name/avatar to appear as the message author. Put their private URLs in `DISCORD_WEBHOOK_URLS` as one JSON object, for example `{"123456789012345678":"https://discord.com/api/webhooks/…"}`. Each webhook is checked against its channel and the configured server at startup. Legacy `DISCORD_WEBHOOK_URL` plus `DISCORD_CHANNEL_ID` still work for one channel, and do not limit channel discovery. Sender banners are omitted: Discord webhooks support names and avatars, but no per-message profile banner. The bot can have a shared profile banner. Channels without a configured webhook use the bot identity and a Flux sender label; new forum posts also use that labelled bot identity.
3. **Firebase sign-in:** in project `aggw-themes`, enable Authentication → Email/Password and add the Flux site's domain to authorized domains. Flux's Profile page now has sign-in/create-account controls. The server verifies Firebase ID tokens, including revocation checks; tokens and account identifiers are never accepted from request bodies.
4. **Private storage:** the existing Spark project can use its **`(default)`** database, provided its client rules deny every path under **`bridgePrivate`**, including nested messages. The rules inspected on October 18, 2026 allow specific existing collections and grant no access to `bridgePrivate`; the Rules Playground denied a private-path read for both an anonymous request and a simulated signed-in user. Set `BRIDGE_FIRESTORE_DATABASE=(default)` for this setup. Review the rules again before deployment and after any rules change: a broad wildcard allowing reads/writes would expose private bridge data. An explicit `match /bridgePrivate/{document=**} { allow read, write: if false; }` can document the restriction, but does not override another matching allow rule. **Do not publish the included deny-all `firestore.rules` over the existing default database**; that file is only for a dedicated bridge database. A separate named database remains an option with the Blaze billing plan, by setting its name explicitly. Create a private server service account with the required Firestore read/write access and Firebase Authentication permission to check token revocation. Keep its JSON key outside the repository, with restricted file permissions. See [Firebase rule matching](https://firebase.google.com/docs/rules/rules-behavior).
5. **VM worker:** install Node.js 22.12+ and copy this `discord-bridge` folder to the VM. Run `npm ci`, copy `.env.example` to `.env`, and fill it in. `GOOGLE_APPLICATION_CREDENTIALS` is the absolute path to the private service-account JSON. `FLUX_SITE_ORIGIN` is the exact website origin, for example `https://flux.example`, without a path. `BRIDGE_PUBLIC_URL` is the HTTPS address you give this worker. Keep `.env` private.
6. **HTTPS routing:** expose this worker's `127.0.0.1:3032` through your reverse proxy or tunnel, including `/api/` and `/media/`. Allow POST bodies up to 1.1 MB and an AI response timeout of at least 130 seconds. Add edge rate limits for `/api/` and `/media/`; the service also applies per-account send and AI limits. Keep the Wisp proxy's existing address and service unchanged. Run one community worker under a process manager/systemd and start it with `npm start`.
7. **Website address:** set `window.FLUX_DISCORD_BRIDGE_URL` in `js/discord-config.js` to the worker's public HTTPS address, then publish the website. No bot token, webhook URL, or service-account key belongs in website files. The worker folder is excluded from the static Vercel upload.

## Discord channels, announcements and forums

The channel list discovers the configured server's channels and categories automatically. Website accounts see channels readable by the server's **`@everyone` role**, with readable history; staff-only channels, private threads, and channels the bot cannot read are excluded. A signed-in website account is not proof that the person has a particular Discord role, so role-restricted channels are not shared. Server-specific membership/verification roles would require a separate linked-account access model before mirroring their restricted channels.

If ordinary members cannot send in a channel, Flux marks it as an **announcements** channel and disables posting. The service also checks permissions for every history read and immediately before sending, including webhook sends. A bot's broader permissions cannot override the website restriction. If members can post but the bot cannot, the channel is read-only until the bot's permission is fixed.

Public text channels, Discord announcement channels, forum/media channels, public threads and the text chat attached to voice/stage channels are supported. Voice/audio itself is not relayed. Forum parents display their posts; opening a post shows that conversation. New posts require a title and any required non-moderator forum tag. Active and archived public posts are discovered; locked conversations stay read-only. Thread replies use Discord's separate **Send Messages in Threads** permission. Channel metadata refreshes within 30 seconds; messages poll every eight seconds. Each channel has a separate recent history of up to 50 messages.

References: [Discord channel permissions](https://github.com/discord/discord-api-docs/blob/main/developers/topics/permissions.mdx), [Discord forums and threads](https://github.com/discord/discord-api-docs/blob/main/developers/topics/threads.mdx).

## Ollama on the VM

Gemini is not required. Install Ollama from its official site on the VM and pull a local model that fits its RAM/GPU, then set `OLLAMA_MODEL` to the exact installed model name. For an initial small-model trial, the official FAQ uses `llama3.2`; review its download size/license before pulling it. Keep `OLLAMA_URL=http://127.0.0.1:11434`; the browser calls this service, which calls Ollama locally. Do not publicly expose Ollama's port. Set `OLLAMA_NO_CLOUD=1` if you want local-only operation.

The local model has no per-request provider API charge, but the VM's compute/storage still cost whatever your host charges. CPU inference works but may be slow or compete with the browser proxy. I have not inspected the VM's hardware, so performance is unverified. If necessary, move Ollama to a more capable machine and use a private network connection. This implementation limits requests to 512 output tokens and one active model request per worker. Leave `OLLAMA_MODEL` blank to keep Assistant unavailable until ready. No cloud fallback is configured.

To have Flux AI recognize the creator, set `FLUX_CREATOR_UIDS` in the bridge's private `.env` to a comma-separated list of the creator's Firebase Authentication UIDs. The service checks these against the verified sign-in token, not the user-supplied display name or chat text. The AI receives only whether the signed-in account is recognized, not the UIDs themselves. Leave the setting empty to recognize no accounts. This changes conversational context only and grants no administrative permissions.

The Home page's Hot list uses aggregate game-open counts stored under the server-only `bridgePrivate/game_statistics/games` collection. Both signed-in visitors and guests contribute; only a known catalog game ID is stored, not an account ID or IP address. Counts start when this feature is enabled; old site-wide counts are not available. The public read and recording endpoints are origin-checked and rate-limited, though automated traffic can still affect popularity. A Firestore write occurs for each recorded opening, so review usage and costs before enabling the service publicly. Keep the complete Flux game catalog (`data.js`) beside the `discord-bridge` folder on any host running this service.

References: https://docs.ollama.com/faq and https://docs.ollama.com/api/chat

## How private Discord conversations work

Sign in on Flux → Chat → Discord DM → **Invite Discord contact**. Privately share the generated code and the bot's Discord profile with your intended contact. They DM the bot `!flux CODE` within ten minutes to consent. Codes are random, single-use and replaced by a new invite. They must be able to DM the bot (Discord privacy/server settings may block DMs).

Once accepted, Flux messages reach that contact from the **Flux bot**, clearly labelled with the Flux sender name. The contact's replies to the bot appear only in that signed-in Flux account's DM view. `!unlink` in Discord or **Disconnect contact** in Flux ends the mapping. Each Flux account and Discord recipient can have one active private pairing at a time, so replies cannot be mixed between senders. Disconnect before pairing another contact; new pairings have separate histories. This is not a collection of separate Discord accounts. User display names are chosen profiles, not proof of Discord identity.

DMs are private from other website users through the authenticated service, not end-to-end encrypted. The bot/server operator and Discord process their content. Old histories remain in the private database after disconnect and are not shown to new pairings. The operator should set an appropriate retention policy; uploaded profile media are public via their unlisted media URLs and should not contain private information. Expired invitation records and obsolete profile media need periodic cleanup.

## Verification before going live

- `npm test` checks request authentication, private history isolation, invitation lifecycle, per-account limits, profile validation, and the Ollama request contract. These tests use fake Discord/model transports and an in-memory database transaction adapter.
- Sign in with two different Flux accounts. Send a unique message in Discord Chat and reply in Discord. Confirm sender avatars and that no profile-banner image cards are attached. Verify the selected Discord channel only is shown.
- Pair account A to a consenting Discord contact; send both ways. Account B must see no private messages. Reuse an accepted code and an expired code; both must fail. Disconnect and verify future Discord replies do not reach Flux.
- Send an Assistant prompt and check the VM's memory/CPU and response time. Keep Ollama loopback-only.
- Test the game Fullscreen button in a browser: only the player should fill the display. Escape returns to the site. Check profile picture crops on a phone-sized screen too.

### Website profile cards

Click a sender's name or avatar in website chat to open their profile. New Flux messages share a snapshot of status, pronouns, bio and accent color, along with the name/avatar. Discord messages provide their author name and avatar; older messages may not have the extra Flux details. Details reflect the profile when the message was sent. Only these public fields are shared; account email and credentials are excluded. Discord message profile snapshots stay in server-only storage and are returned with the matching channel history. Profile banners are removed from the website.

New messages and the last 50 messages in each shared channel are supported. Edits/deletions appear on the next poll; private messages are captured while the worker is connected. Private edits, deletions, reactions, and downtime recovery are not implemented. Message sends are not exactly-once: retrying after an uncertain failure may duplicate a send. Keep this as a draft until real credentials and live Discord/Firebase/PC checks have passed.
